# 山丘上的卡菲卡（Hills）功能規劃

> 版本：v1.30 · 2026-11-09 · 狀態：M0 完成，進入 M1
> 本文件是專案的最高層事實來源；修改專案前先修改本文件（見 [AGENTS.md](../AGENTS.md)、[docs/README.md](./README.md)）。

## 1. 產品定位

Hills 是 CAFECA 團隊的工作通訊與協作工具，安裝於桌機、筆電與手機，以 P2P 技術串聯成員裝置。它把「溝通」與「計劃 / 執行 / 回報」放在同一個地方：

- **看得到團隊**：誰在線、誰在開會、誰請假、各自屬於哪些小組、此刻在做什麼。
- **對得齊目標**：個人年度 → 季度 → 月度 → 週度目標逐層拆解，週目標再拆成任務，任務完成自動推動目標進度，並與每日 Scrum 連動（D46）；個人目標對齊小組與公司方向，大家都看得到誰往哪裡走（D47）。
- **說得上話**：即時訊息、檔案傳遞、語音 / 視訊通話與螢幕分享。
- **有 AI 幫手**：每個人、每個聊天群組都可配置 AI 助理，協助整理計劃、撰寫報告、摘要討論。

| D46 | 任務是目標的最底層 | **目標為年 / 季（OKR）、月 / 週（待辦）四層，取消日層級；週目標往下拆成任務**：任務可連結一個週目標（選填，零碎任務可不連結），任務進度 = 已完成步驟比例（沒有步驟時完成 100、未完成 0），週目標有連結任務時進度為任務平均；**任務可設為私人**（只有自己看得到）；目標頁第五欄改為「任務」 | 原設計目標與任務並行、日目標與任務重疊、任務完成不計入目標；修改 D8；細節見 technical-design §16.8、§16.10，ui-spec「目標」「任務」 |
| D47 | 引導式目標與團隊方向 | **目標頁預設為引導式**（設計「目標拆解流程改版」方案 C：白話用語、一次問一件事的規劃精靈、首頁直接提示下一步、這一週是一張清單、建立可復原），**熟手可切換為「進階檢視」路線圖**（方案 B：時間軸 + 關鍵結果泳道、拖曳建立與改期間、一次拆解），取代 D43 的「階梯」，切換記在本機；**方向分三層**：公司方向（管理者設定）→ 小組目標（小組負責人設定，對齊公司方向）→ 個人年 / 季目標（對齊小組目標或公司方向）；**全員透明**：所有成員都看得到團隊方向與每個人的方向；**四項檢查**標示「可能偏離」：這週完成的事為了團隊方向的不到 50%、進度落後經過時間 25 個百分點以上、14 天沒有更新、這一季沒有目標對齊團隊方向（門檻由管理者調整）；**每個人的 App 計算並發佈自己的方向摘要**（比例、進度、季目標標題、最近幾週的軌跡；不含任務內容，私人目標與私人任務只算進比例、不露標題）；以「方向羅盤」呈現（傾斜地面上每人一條箭頭與角色人像，角度 = 時間花在哪裡、長度 = 進度，滑過看摘要）；對他人只能送出「建議對齊」，由本人決定是否修改 | 原介面學習曲線高、拆解難操作；看不出團隊與個人方向是否一致。任務與小組目標以小組金鑰加密，跨小組讀不到，所以由本人發佈摘要；摘要讓全員看到比例與季目標標題是刻意的取捨，伺服器仍看不到內容。分五批交付（引導式與方向 → 摘要與羅盤 → 路線圖 → 週一方向時刻與軌跡 → 延伸想法）；細節見 technical-design §16.14，ui-spec「目標」 |
| D48 | 本機 MCP 介面 | **桌機 app 內建本機 MCP 伺服器，讓使用者自己的 AI Agent（Claude Code、Claude Desktop 等）協助操作 Hills**：只綁 127.0.0.1、以本機 token 驗證；Agent 只能做使用者本人在 app 內能做的事（讀目標、方向、任務、Scrum、報表、訊息、知識庫）；**所有寫入（新增 / 修改 / 刪除目標與任務、Scrum 草稿、送出訊息、新增 / 刪除知識）先成為「待確認變更」，使用者在 Hills 的確認卡核准後才寫入**（D17）；預設關閉，**管理者在組織設定開放後**，成員才能在自己的裝置開啟，開啟時提示資料會交給外部 AI 服務、離開 Hills 的端對端加密 | 讓既有 AI Agent 幫忙整理進度、分工與寫 Scrum，不必等 M3 的 AI Gateway；Agent 讀到的資料會送到它自己的模型服務，因此需組織同意與本人選擇；寫入一律在 Hills 內確認，不論 Agent 端怎麼設定都不會被自動修改。細節見 technical-design §18、ui-spec「設定」「AI 代理確認卡」 |
| D49 | 小組管理與小組金鑰交接 | **管理者建立、改名、封存小組；管理者與該小組負責人可加入 / 移出成員、設定負責人**（小組至少一位成員）；**小組金鑰（TK）由小組成員的裝置自動交接**：持有 TK 的成員裝置發現小組名單上有人還沒拿到，就把全部 epoch 封裝給他；有人被移出時由「指定輪替裝置」（負責人中 memberId 最小者，沒有負責人時取成員中最小者；該成員裝置中公鑰最小的一台）輪替新 epoch；**管理者不持有非所屬小組的 TK**（建立小組時產生第一個 epoch 封裝給成員後即丟棄） | 讓負責人自己管理小組、管理者不必在線；管理者不在小組就讀不到小組任務，符合最小權限。代價：mailbox 看不到小組名單，改為接受任何有效成員封裝的小組金鑰，成員資格由收件端檢查；新加入者要等一位小組成員上線才能讀到小組內容。細節見 technical-design §16.15，ui-spec「設定 → 成員與小組」 |
| D50 | 組長分派任務 | **任務頁加「依成員」分派板**（未指派欄 + 每位成員一欄，欄頭顯示負荷，拖曳或選單指派；只有負責人與管理者能指派）；**指派時看見負荷**（未完成、本週到期、休假、這週有沒有週目標）；**從小組目標一次拆給多人**；**被指派者收到通知，回應「接下」或「有困難」**（有困難會私訊指派者）；**接下時由本人選擇或建立自己的週目標**，組長不替成員寫目標；「偏重」= 未完成 ≥ 7 件或本週到期 ≥ 4 件（固定值，之後可改為組織設定） | 組長看不到負荷、對方不知道被指派、任務接不上目標、一次只能建一件。週目標仍只由本人建立，維持 D47 與 D17 的精神。細節見 technical-design §16.8 v0.26，ui-spec「任務 → 分派（D50）」 |

## 4. 系統架構概覽

```
┌───────────── 成員裝置（桌機 / 筆電 / 手機）─────────────┐
│ UI 層  ── 計劃 / Scrum / 聊天 / 通話 / AI 助理            │
│ 同步層 ── 本地資料庫 + CRDT（計劃、任務、訊息）            │
│ 安全層 ── 裝置金鑰、端對端加密（群組金鑰管理）            │
│ 傳輸層 ── P2P：WebRTC DataChannel / Media、libp2p 類協定 │
└──────────────────────────────────────────────────────┘
          │ 直連（優先）              │ 無法直連時
          ▼                          ▼
┌──────── 基礎設施（可自架）────────────────────────────┐
│ iroh-relay：連線協調、NAT 打洞輔助與中繼（取代 Signaling + TURN）│
│ Presence 服務：上線狀態廣播、可信時間戳簽發             │
│ 離線信箱節點：暫存加密訊息，對方上線後投遞（不可解密） │
│ 儲存節點 ×8：SwarmStorage 原理的檔案分片（只存密文分片）     │
│ SFU（LiveKit）：≥5 人視訊會議時轉發媒體流              │
│ AI Gateway（選配）：統一呼叫雲端 LLM、套用政策與稽核   │
└──────────────────────────────────────────────────────┘
```

技術方向：

- **客戶端**：Tauri 2，單一程式碼庫涵蓋 macOS / Windows / Linux / iOS / Android（M1 先發佈三個桌機平台）；Rust 核心負責 P2P、加密、本地資料庫（SQLite）與 CRDT，前端 React + TypeScript。
- **P2P 傳輸**：iroh（QUIC，內建打洞；直連失敗時經自架 iroh-relay 中繼，流量仍端對端加密）。
- **資料同步**：本地優先（local-first），以 Automerge 合併多裝置與離線編輯；同步經 iroh 連線傳輸。
- **加密**：裝置級 Ed25519 身分金鑰；一對一與群組訊息端對端加密（群組可採 MLS 協定）；信箱節點與 Relay 只看得到密文。
- **部署**：單一 `docker-compose.yml` 包含 iroh-relay、Presence / 時間戳服務、信箱節點、AI Gateway、LiveKit 與反向代理（自動 TLS 憑證）；建議部署於台灣區雲端主機（GCP / AWS），附備份與監控腳本。
- **設計系統**：定義色彩 token（淺 / 深兩套）、字型（繁中以思源黑體 / Noto Sans TC 為主）、間距與元件；前端以 Tailwind + 自訂元件庫實作，主題色由組織設定覆寫。
- **可設定性（開源需求）**：組織名稱、Logo、主色、預設語言、時區、假日曆來源、假別、打卡規則皆為組織設定，程式碼中不得寫死 CAFECA 專屬值。
- **行動裝置背景限制**：iOS / Android 背景無法常駐 P2P，需以推播（APNs / FCM）喚醒，推播內容僅含加密通知。

## 5. 功能模組

### 5.1 身分、組織與工作小組

- **以 CAFECA 登入（D41）**：成員身分是 CAFECA 帳戶，Hills 不另設帳號密碼。新成員取得組織連線碼後以 CAFECA 登入、送出加入申請，管理者核准時指定角色與小組。
- 新裝置以 CAFECA 登入，由本人其他在線裝置自動授權（多裝置綁定），其他裝置會收到「新裝置已加入」通知並可撤銷；同一成員的各裝置共用一個成員身分。
- **還原**：遺失所有裝置時，以 CAFECA 登入申請還原，管理者核准後換發成員金鑰，其他成員自動把小組與對話金鑰重新分享給新金鑰；只有本人可讀的私人資料無法還原。
- **離職處理**：管理者一鍵停用成員 → 撤銷全部裝置、群組金鑰輪替、移出所有小組，並保留其計劃與報表供交接。
- 成員個人檔案：姓名、職稱、時區、工作時段、技能標籤。
- **工作小組**：一人可屬多個小組；小組有負責人、目標與專屬頻道。管理者建立、改名、封存小組；管理者與該小組負責人管理成員與負責人；小組金鑰由小組成員的裝置自動交接，管理者不在小組就讀不到小組內容（D49）。
- 管理者權限保護：組織至少需 2 位管理者，重要操作（停用成員、變更政策）需第二位管理者確認（選配）。
- 組織架構檢視：依小組 / 成員瀏覽，顯示每人所屬小組。
- 裝置遺失處理：撤銷裝置金鑰、強制群組金鑰輪替。

### 5.2 出勤與即時狀態（Presence）

- 狀態：上線、忙碌、會議中、專注中、午休、暫離、休假、離線（D40：新增午休，外出改稱暫離，請假狀態顯示為休假）；可自訂狀態文字與到期時間（到期時間即「幾點回來」，顯示在角色名牌上）。
- **自動狀態**：通話中自動標為「會議中」；閒置 N 分鐘轉「暫離」；組織設定的午休時段內可一鍵切換「午休」（不自動切換）；行事曆（後期整合）自動帶入。
- **打卡規則**（組織可設定）：彈性上班區間（預設 08:00–10:00）、每日應工作時數（預設 8 小時）、休息時間（預設 1 小時不計工時）；晚於彈性區間上班即標示遲到，未滿應工作時數即標示早退 / 工時不足。
- **上下班打卡**：手動打卡為正式紀錄，「首次上線 / 最後離線」作為參考與忘打卡提醒；補打卡需主管核准。
- **打卡防竄改**：打卡紀錄以裝置金鑰簽章並帶可信時間戳（由 Signaling / 信箱節點簽發），離線打卡上線後補簽並標註。
- **請假**：假別（特休、事假、病假等，可由管理者自訂）、期間、代理人、附件；送出後依核准規則流轉：預設由小組負責人核准；管理者可設定第二層規則（例：連續超過 3 天、特定假別需管理者再核准），負責人本人請假則上送管理者。核准結果同步至團隊行事曆與 Presence，代理人同步收到通知。
- **預設假別**（台灣勞基法範本，組織可增刪、調整）：特別休假、事假、普通傷病假、生理假、婚假、喪假、產假、陪產檢及陪產假、公假、公傷病假、補休；各假別設定是否給薪、最小請假單位（預設 1 小時）、年度上限、是否需附證明。
- **特休額度**：依到職日以週年制自動計算（依勞基法年資級距），顯示已用、剩餘與到期日；未休特休到期提醒。
- **加班申請**：事前或事後申請加班時段與事由，經多層核准後生效；可選加班費或補休，補休時數轉入「補休」假別額度。未申請的超時工時只列為參考，不計為加班。
- **工時統計**：每日 / 每週 / 每月工時、加班時數、遲到早退標示；個人可看自己，負責人可看組員，管理者可匯出 CSV / Excel。
- **打卡地點標註**：裝置連線至管理者登錄的公司 Wi-Fi（SSID / BSSID）時標為該 Wi-Fi 所屬的辦公室（組織可登錄多個辦公室，例如「台北辦公室」「新竹辦公室」，D40），否則標為「遠端」；成員可手動切換或選擇不顯示地點；地點只作標註，不阻擋打卡，也不收集 GPS 座標。
- 工時可對應任務：Scrum 中「進行中」任務的時間可作為參考工時分配（選配）。
- **團隊看板**：一頁看全員狀態 + 所屬小組 + 「目前正在執行的任務」（來自 5.4）。
- 隱私：成員可設定狀態與正在執行任務的可見範圍。

### 5.3 個人計劃（年 → 季 → 月 → 週 → 任務）

- **四層目標 + 任務**（D46）：每層目標可連結上層目標，形成目標樹；週目標往下拆成任務（§5.4），任務是最底層。上層進度由下層自動彙總。
- **格式**：年度 / 季度採 OKR（目標 + 2–5 個可衡量的關鍵結果，含起始值、目標值、目前值）；月 / 週採待辦項目，可連結到某個關鍵結果。
- **進度彙總**：任務（依完成步驟比例）→ 週 → 月的完成度自動彙總至關鍵結果與目標，亦可手動覆寫關鍵結果數值。
- **拆解輔助**：AI 助理協助把季度目標拆成月度里程碑、週任務。
- **回顧**：每週、每月結束時引導填寫回顧（完成、未完成原因、調整），AI 先產生草稿。
- 可見度：**預設小組可見**；可逐項改為私人或全組織可見。
- 小組目標：小組負責人可設小組層級目標，成員個人目標可對齊至小組目標。

#### 團隊方向（D47）

- **三層方向**：管理者設定公司方向（每年 1–3 個）；小組負責人設定小組目標並對齊一個公司方向；成員的年 / 季目標對齊一個小組目標或公司方向（選填，規劃精靈會依標題相近度建議）。
- **進度**：小組目標 = 對齊它的個人目標進度平均；公司方向 = 對齊它的小組目標與直接對齊的個人目標平均（只計算讀者看得到的）。
- **引導式介面**（預設）：首頁依時間提示下一步（年底規劃明年、月初分到月、週一排這週、空著的季到期前提醒）；規劃精靈「想達成什麼 → 為了團隊哪個方向 → 分到四季 → 確認」，月 / 週用同樣的「分到下一層」；這一週是一張可打字新增的清單；建立後可「復原」。**進階檢視**為路線圖（D47）。
- **方向摘要與偏離**（第 2 批）：每個人的 App 發佈方向摘要（這週完成的事中為了團隊方向的比例、季目標與進度、最後活動）；團隊頁以方向羅盤與清單呈現誰在路上、誰可能偏離，點人看四項檢查的依據；可以對沒對齊的人送出「建議對齊」，由本人決定是否套用。規則見 technical-design §16.14。

### 5.4 每日 Scrum 與任務

- 每日回報表單：**昨天完成、今天計劃、遇到的阻礙**；可從「今天的任務」一鍵帶入（D46）。
- 任務：標題、所屬小組、負責人、狀態（待辦 / 進行中 / 審核 / 完成）、預估時間、期限、步驟（每步可有負責人與完成狀態）、**所屬週目標**（選填，D46）。
- **私人任務**（D46）：任務可設為私人，只有自己看得到、不屬於任何小組，其他規則與小組任務相同。
- **焦點**（D40）：首頁自動選出每人今天最需要聚焦的一件任務（排序：期限最近 → 卡住別人 → 指派給你 → 被提及），可手動更換，同時只有一件。
- 看板 / 清單兩種檢視；「開始執行」一個任務時自動更新 Presence 的「正在執行」。
- **分派**（D50）：負責人在任務頁「依成員」檢視把任務拖給成員，或從小組目標一次拆給多人；選負責人時看得到對方的未完成件數、本週到期與休假；被指派者收到通知，按「接下」（選或建立自己的週目標）或「有困難」（附一句原因，私訊指派者）。
- 阻礙自動通知小組負責人，並可一鍵開啟討論串。
- 提醒：工作日固定時間提醒填寫 Scrum；未填寫者在小組頁面標示。
- **工作日判定**：組織假日曆（預設台灣，依行政院人事行政總處公告的國定假日與補班日，每年匯入）→ 扣除成員請假日 → 依成員時區與工作時段決定提醒時間；管理者可另加公司自訂假日。

### 5.5 自動報表

- **日報 / 週報 / 月報 / 年報**：依 Scrum 回報、任務完成紀錄、計劃進度自動生成。
- **固定欄位**（日報 / 週報）：
  1. 完成 / 進行中 / 阻礙（來自 Scrum 與任務狀態）
  2. OKR 進度（本期關鍵結果數值變化）
  3. 工時與出勤摘要（工時、請假、加班）
  4. 下期計劃（明日 / 下週的計劃項目）
- 月報 / 年報沿用上述欄位並彙總，另加「目標達成率」與「回顧」。
- 個人報表與小組彙整報表兩種；M1 以範本自動填入，M3 起由 AI 產生摘要、亮點、風險與下期建議。
- **發佈對象**：個人週報 / 月報預設發佈至所屬小組頻道（小組全員可見），使用者可在發佈前改範圍。
- 產出後可編輯、再發佈至小組頻道，或匯出 Markdown / PDF。
- 年報可回顧年度目標達成率與季度演進。

### 5.6 即時通訊

**M1（D34）**

- 一對一、群組對話；Markdown 與程式碼區塊、表情符號、@提及。
- 檔案與資料夾附件（§5.7）。
- 桌機新訊息通知；多裝置同步與離線補傳（透過信箱節點）。

**M2**

- 小組頻道、討論串回覆、表情回應、已讀狀態。
- **歷史訊息**：新成員加入時，線上的既有成員裝置自動將群組歷史金鑰加密分享給新成員，再由新成員向其他節點同步歷史；群組可設為「僅加入後」以停用此行為（敏感群組建議開啟）。
- 訊息編輯 / 撤回、釘選、書籤。
- 本地全文搜尋（訊息加密儲存，於本機建立索引）。
- 訊息與任務互轉：把一則訊息轉成任務或計劃項目。

### 5.7 檔案傳遞

**M1（D35、D36）**

- **SwarmStorage 原理**：前端逐一讀取檔案 → 每 20 MB 條帶 AES-256-GCM 加密 → Reed-Solomon (8, 5) 切成 8 個分片 → 上傳到 8 個自架儲存節點；任意 5 片即可還原，最多容忍 3 個節點故障。
- 每個檔案一把隨機金鑰；金鑰與檔案清單只存在加密的對話訊息中，儲存節點只看得到分片密文。
- **檔案或資料夾**：可選擇多個檔案或直接選擇本地資料夾；資料夾以一次性快照分享（含目錄結構）。
- 收件者可下載整個資料夾或單一檔案；所有分片驗證通過後才寫出完整檔案（`.partial` 暫存後改名）。
- 上傳 / 下載進度、暫停、續傳、取消。
- 寄件者離線時收件者仍可下載。
- **保留政策**：訊息永久保留；儲存節點上的分片預設 1 年後清除（管理者可調整），已下載到成員裝置的副本不受影響。

**M2**

- 群組檔案區：列出對話中分享過的所有檔案。
- 圖片 / 影片 / PDF 預覽。
- 行動端上傳與下載。

### 5.8 語音 / 視訊通話

- 一對一語音 / 視訊、群組通話；2–4 人 P2P mesh，第 5 人加入時無縫切換至自架 LiveKit SFU。
- SFU 模式下媒體流於伺服器端轉發；可啟用 LiveKit 端對端加密（Insertable Streams），但伺服器端錄影需關閉此選項，由會議發起人選擇。
- 螢幕分享、會議中聊天、舉手、靜音控制。
- 錄音 / 錄影（需全員同意提示；SFU 模式於伺服器端錄製，P2P 模式由發起人本機錄製），AI 產生會議摘要與待辦事項，可直接轉成任務。
- 從群組或行事曆排定會議。

### 5.9 AI 助理

**個人助理**（每人一位，僅能存取本人資料）

- 計劃教練：拆解目標、檢查計劃是否具體可衡量、提醒落後項目。
- 每日 Scrum 草稿：根據昨日任務與訊息產生回報草稿，使用者確認後送出。
- 報表撰寫：日 / 週 / 月 / 年報摘要與回顧。
- 訊息摘要：「我不在時發生了什麼」。

**群組助理**（每個聊天群組可選配）

- 被 @ 時回應；可設定角色（如：專案秘書、技術顧問、會議記錄）與自訂指令。
- 討論摘要、決策紀錄、待辦擷取並指派。
- 存取範圍僅限該群組訊息與檔案；群組成員可見助理的設定與資料範圍。

**主動提醒**（皆可個別關閉，人在迴路中）

- 計劃落後：關鍵結果進度低於時間進度時提醒並建議調整。
- Scrum 未填：工作日提醒時間未填寫時提醒，並附上草稿。
- 待辦逾期：任務或會議待辦逾期時提醒負責人。
- 週期結束：週五 / 月底自動準備報表與回顧草稿，等待確認後發佈。
- 原則：AI 只能「提醒」與「產生草稿」，任何發送訊息、修改計劃 / 任務、發佈報表皆需使用者按下確認。

**模型與政策**

- **AI Gateway**：組織統一 API Key 只存放於 Gateway，客戶端不持有金鑰；Gateway 負責身分驗證、用量計算、政策檢查與稽核。
- 每個助理可選雲端模型（經 Gateway）或本地模型（如透過 Ollama 於桌機執行）。
- 管理者可設定：哪些群組禁止使用雲端模型、是否保留 AI 對話紀錄、每月用量上限。
- AI 永遠不代替使用者發送訊息或修改計劃，除非使用者確認（人在迴路中）。

### 5.10 外部整合

- **Google Calendar**（OAuth，由成員個人授權）：會議時段自動切換 Presence 為「會議中」；核准的請假寫入行事曆；從 Hills 排定會議時建立行事曆事件並附上通話連結。
- **GitHub**（GitHub App，組織層級安裝）：成員的 PR、Issue、Commit 活動自動帶入 Scrum 草稿；任務可連結 Issue / PR，PR 合併時任務自動標為完成（需確認）；Repo 事件可推送至指定頻道。
- 整合憑證存放於 AI Gateway 同層的整合服務，不存於客戶端。
- 後期：Jira / Linear、Slack 匯入。

### 5.11 通知

- 依類型設定：提及、私訊、阻礙、Scrum 提醒、報表完成。
- 勿擾時段與專注模式；行動端推播只顯示「有新訊息」，內容於裝置解密後才顯示。

### 5.12 管理後台

- 成員與裝置管理、加入與還原申請核准、成員停用與交接。
- AI 政策、檔案保留期限、Relay / 信箱節點設定。
- 公司 Wi-Fi（SSID / BSSID）登錄。
- 請假核准規則（層級、天數門檻、假別）。
- 檔案保留期限、GitHub App 安裝與頻道推送設定。
- 假別與特休規則、打卡規則（上班時段、彈性時間）、請假核准流程設定。
- 出勤與工時統計匯出。
- AI 用量儀表板（依成員 / 群組）。
- 稽核紀錄（管理操作，不含訊息內容）。

### 5.13 知識庫（D42）

- **全組織一個知識庫**：成員可新增知識（標題、內容、標籤、來源），所有成員可讀。
- **歸納分類**：知識歸在「分類 → 主題」之下；分類與主題由成員建立、改名、合併。
- **關聯**：引用（手動連結）、同主題、同任務（來源為同一任務）、同對話（來源為同一對話），以不同顏色與線型呈現。
- **來源**：手動新增、從對話訊息「存成知識」、從分享的檔案建立；保留來源連結。
- **知識圖譜（星空）**：每個分類是一個星座，星星大小代表被引用次數；選取知識時顯示關聯與預覽卡片；底部時間軸顯示每週新增數量，可拖曳回看；另有清單檢視。
- **M1**：手動版（上述全部，不含 AI）。**M3**：AI 從對話與檔案歸納出待確認的知識與分類、關聯建議，使用者按「套用」才寫入（D17）。

### 5.14 AI 代理（MCP，D48）

- **本機 MCP 伺服器**：桌機 app 開啟後在 `127.0.0.1` 提供 MCP（Streamable HTTP），使用者把自己的 AI Agent 連上即可請它查詢與整理目標、方向、任務、Scrum、報表、訊息與知識庫。
- **寫入要確認**：Agent 的新增與修改都先成為「待確認變更」，Hills 右下顯示確認卡，使用者核准後才寫入；拒絕或 24 小時未處理即作廢。
- **雙重開關**：管理者在組織設定「允許成員使用 AI 代理」，成員再於自己的裝置開啟（預設關閉）；管理者關閉後各裝置立即停止。
- **範圍**：只做本人在 app 內能做的事；不提供金鑰、裝置、成員管理、組織設定與檔案下載。本機只記錄工具名稱、時間與結果，不記內容。

### 8.1 小團隊（1–2 人）開發策略

- **不自行實作協定**，以成熟函式庫組裝：
  - P2P 連線：iroh（Rust，內建打洞與 Relay 伺服器，可大幅取代自建 Signaling + TURN）
  - 資料同步：Automerge 或 Loro（Rust 原生 CRDT）
  - 群組加密：M1 先用「每小組一把對稱金鑰 + 成員公鑰封裝分發」；M2 有聊天時再評估 OpenMLS
  - 視訊：LiveKit（M4）
- **M1 範圍**：依 D27 保留完整假勤（多層核准、特休自動計算、桌機 Wi-Fi 識別、可信時間戳）；依 D34 加入一對一 / 群組對話與 SwarmStorage 檔案分享。行動端 Wi-Fi 識別隨 M2 行動端上線。
- **控制範圍的方式**：M1 只做對話與檔案分享的基本功能（D34 列出的進階功能在 M2）；不做通話、AI；報表先用範本產生，AI 摘要在 M3 才加入；只發佈 macOS 與 Windows。
- **重用 SwarmStorage**：Reed-Solomon 編碼直接參考 SwarmStorage 的 `reed_solomon_erasure.ts`（MIT），在 Web Worker 中執行；效能不足時改用 WASM。
- **AI 輔助開發**：規格文件與資料模型先定稿，以 AI 產生樣板程式碼與測試；人力集中在 P2P / 同步 / 加密等核心。
- **粗估時程**（1–2 人，全職）：M0 約 6–8 週（含 PoC 2–3 週）、M1 約 18–24 週（含對話與檔案約 6–8 週）、4 週試用，約 **8–9 個月**可完成 M1 驗收。

## 9. 主要風險

- **行動端背景 P2P 限制**：需仰賴推播喚醒與信箱節點，否則手機收不到訊息。
- **群組端對端加密的複雜度**：成員進出、裝置撤銷時的金鑰輪替，建議採用成熟函式庫而非自行實作。
- **AI 與端對端加密的衝突**：雲端 AI 必須看到明文；需明確告知並由群組政策控管。
- **假勤法規正確性**：特休級距、各假別天數與給薪規則需在實作前對照現行勞基法與性別平等工作法，並於法規修訂時更新範本。
- **打卡紀錄的法規效力**：若需作為正式出勤紀錄，需確認保存年限與可匯出格式符合勞動法規。
- **行動端讀取 Wi-Fi 名稱的限制**：iOS 需取得位置權限與 Access WiFi Information 權限，Android 10 以上也需位置權限；使用者拒絕時一律標為「遠端」。
- **SFU 與端對端加密的取捨**：伺服器端錄影與 AI 會議摘要需看到明文媒體流。
- **依賴 CAFECA 身分（D41）**：CAFECA 帳戶遭盜用等同取得 Hills 身分；CAFECA 錢包或鏈上 RPC 無法使用時，新成員、新裝置與還原都會暫停（已登入的裝置不受影響）。遺失全部裝置時只有本人可讀的私人資料無法還原。CAFECA 合約層的 ERC-7739 防重放尚未完成，正式試用前需確認。
- **歷史訊息分享的安全性**：分享歷史金鑰等同讓新成員讀取全部過去內容，需在加入時明確提示，並記錄於稽核紀錄。
- **WebView 加密效能**：AES-GCM 由 WebCrypto 執行、Reed-Solomon 在 JS / WASM 執行，macOS（WKWebView）與 Windows（WebView2）效能差異需在 M0 PoC 量測。
- **跨平台路徑**：資料夾分享需處理 Windows 保留名稱、長路徑、大小寫不敏感的檔名衝突與中文檔名正規化（NFC / NFD）。
- **儲存節點集中**：M1 若 8 個儲存節點都在同一台主機，只能防單一磁碟故障，無法防主機故障；正式使用時應分散到至少 3 台主機或不同磁碟。
- **人力不足**：1–2 人負擔 P2P、加密、跨平台與 AI，任一核心技術卡關即延誤整體時程；M0 需先做技術驗證（PoC）。
- **公開 repo 的資安**：開發中的協定與加密設計公開可見；需設定 secret scanning、`.env` 範本化，並在 M5 前完成一次加密設計審查。
- **CRDT 資料成長**：長期訊息歷史需設計快照與修剪策略。
